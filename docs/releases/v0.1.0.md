# Doolittle v0.1.0

Doolittle v0.1.0 is the first public alpha of the local-first ElizaOS agent for
chat, coding, research, automation, connected tools, and operator workflows.
It is suitable for evaluation and daily local use with backups, but it is not
yet a stability or long-term data-format promise.

## Highlights

- One ElizaOS-native runtime across the conversational shell, desktop app,
  local HTTP API, gateways, and task orchestration.
- A persistent desktop workspace with project-scoped chat, Code and Work
  surfaces, interactive terminals, context capsules, review workflows, and
  explicit recovery states.
- Local Ollama support plus provider readiness, model selection, subscription
  and API account pools, MCP tools, Skills Hub, approvals, and runtime
  diagnostics.
- Native messaging adapters route inbound work through the same pairing,
  session, journal, attachment, and policy boundary. Rejected outbound
  deliveries can be retried from their stored payload without rerunning the
  agent or its tools.
- Chat, Code, and Work preserve the selected project, workspace, and chat
  session. Terminal and editor context moves as compact, removable capsules
  instead of replacing the visible draft with raw source text.
- Signed-update plumbing, bounded private attachment storage, encrypted secret
  storage, loopback-first networking, and isolated Electron renderer IPC.
- Cancellable voice and media operations stop sender-scoped work when the user
  cancels, changes media tabs, leaves the route, or closes the renderer.
- A single desktop process owns each private runtime profile; repeated launches
  restore and focus the existing window instead of starting competing stores.

The complete change ledger is in [CHANGELOG.md](../../CHANGELOG.md).

## Supported release artifacts

| Platform | Architecture | Artifact |
| --- | --- | --- |
| macOS | Apple silicon (`arm64`) | DMG and ZIP; notarization is confirmed only by the native macOS release workflow |
| Windows 10/11 | `x64` | per-user NSIS installer with Authenticode |
| Linux | `x64` | AppImage and DEB |

Intel macOS, Windows ARM64, and Linux ARM64 are not v0.1 release targets. A
source checkout remains available for unsupported development hosts, without a
binary-support promise.

## Install and first run

Download the artifact for your platform from the GitHub release, verify its
SHA-256 value against `SHA256SUMS.txt`, then install or run it normally. The
packaged desktop includes its own runtime and does not require Nub, Node.js,
Git, or a source checkout.

Ollama is the default no-key model path. Install Ollama separately and pull the
models shown by onboarding, or configure another provider in **Models** and
**Connections**. Provider packages being present does not imply that an
account, credential, or remote service is ready; Doolittle exposes those states
explicitly.

## Compatibility and persistence

- Doolittle product version: `0.1.0`.
- ElizaOS runtime baseline: exact beta train `2.0.3-beta.7`.
- Existing development builds labeled `2.0.3-beta.7` sort above `0.1.0`, so the
  updater will not treat v0.1.0 as an upgrade. Remove the development app and
  install v0.1.0 manually. Keep the Doolittle profile/data directory if you
  want to retain compatible settings, sessions, and workspace history.
- Back up important work before changing versions. v0.1 does not yet promise
  automatic downgrade migrations or last-known-good updater rollback.

## Security and privacy

Doolittle binds its API to loopback by default. Non-loopback operation requires
an API bearer token, and remote terminal execution uses a separate terminal
token. Credentials remain outside renderer/API projections, managed files have
bounded private storage, and the desktop uses context isolation, sandboxing,
and a transport allowlist.

Report vulnerabilities privately using the process in
[SECURITY.md](../../SECURITY.md).

## Known limitations

- This is alpha software on an ElizaOS beta SDK. Runtime and plugin contracts
  can still change.
- Live research, web search, messaging delivery, MCP servers, and hosted models
  require their own configuration and network access.
- The MIT desktop artifact omits the optional Telegram and WhatsApp native
  plugin dependency closures because their current transitive licenses are not
  compatible with the single-file distribution. They remain available to
  source/CLI installations. Discord voice requires a system ffmpeg/avconv.
- Linux checks releases manually; in-app Linux installation is disabled until
  update metadata has an independently pinned signature. Tagged Windows builds
  bind update metadata to the full Authenticode signer subject.
- Autocoder planning and unsupported providers report unavailable or
  non-executed states rather than simulating success.
- Automatic N-to-N+1 updater rollback is not yet a release guarantee. If an
  update fails, reinstall the prior verified artifact and restore your profile
  backup.
- The broader development-only Eliza dependency graph can contain reviewed
  high-severity advisories in packages that are not shipped by the desktop.
  Release builds inventory emitted runtime bytes and copied native packages,
  block vulnerable versions in that artifact, and stop when a new high
  advisory has not yet been classified. Critical advisories still block the
  complete production graph.

## Artifact provenance

The release attaches `release-manifest.json`, `SHA256SUMS.txt`, per-platform
provenance receipts, and this MIT license alongside the platform installers.
The manifest records the exact source commit, product version, platform and
architecture for every asset. Each receipt binds the native installers and
update metadata to the verified packaged `app.asar` from that platform build;
native jobs compare that payload with the mounted, extracted, or installed
deliverable before upload.
The local `nub run desktop:package:all` command produces the same checksum
companion for its verified cross-platform installer set. It builds into an
isolated staging directory and replaces the prior local set only after all
three platforms, receipts, the manifest, and checksums pass verification.
Local all-platform output performs strict macOS code-signature verification but
does not itself prove notarization; the native macOS workflow requires stapler
and Gatekeeper evidence before publishing a notarized artifact.
The GitHub release is published only after all native platform jobs pass; a
failed platform build must not create a partial public release.
