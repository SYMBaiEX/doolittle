# Native macOS releases

Doolittle's native macOS release includes the GPUI desktop, Rust CLI, bundled
Node.js, and the existing ElizaOS runtime. Both binaries share the runtime in
the app bundle. The CLI is `Doolittle.app/Contents/MacOS/doolittle-native` and
can be symlinked as `doolittle`.

## Build and verify

Run `nub run native:package:mac` for an ad-hoc development bundle. Run
`nub run native:package:mac --release` for a Developer ID distribution bundle.
Use the repository-pinned Node.js distribution and set the release variables
in the signing environment.

| Variable                          | Value                                                                 |
| --------------------------------- | --------------------------------------------------------------------- |
| `DOOLITTLE_MAC_SIGN_IDENTITY`     | Doolittle Developer ID Application certificate name or SHA-1 identity |
| `DOOLITTLE_MAC_NOTARY_PROFILE`    | Xcode `notarytool` keychain profile                                   |
| `DOOLITTLE_MAC_UPDATE_FEED`       | HTTPS URL for the feed for this release channel and CPU architecture  |
| `DOOLITTLE_MAC_UPDATE_PUBLIC_KEY` | Base64 Ed25519 public key generated with Sparkle                      |
| `DOOLITTLE_SPARKLE_ARCHIVE`       | Local copy of the pinned Sparkle 2.10.1 archive                       |

The release command verifies the framework checksum, signs the bundle and
embedded executables, verifies the Doolittle signing team, waits for Apple
notarization, and validates the stapled app with Gatekeeper. It creates the
signed `Doolittle.app` and a ZIP in a unique directory in
`target/native-packages`. Feed publication is a separate operator action.
[Official Sparkle archive](https://github.com/sparkle-project/Sparkle/releases/tag/2.10.1)

## Stage the update

Keep the appcast signing key in the release signing environment. Build an
older baseline and the proposed update with the same staging feed URL and
public key. Increase the root package version between the two builds. Use a
dedicated feed per channel and architecture. The first native release can be
installed manually from its notarized ZIP.

Copy the ZIPs to an isolated staging directory. From the checksum-verified
Sparkle distribution, generate the signed feed with this command. Set the
download prefix to the HTTPS directory serving the ZIPs. The output file name
must match the URL embedded in the builds.

```sh
bin/generate_appcast --account doolittle-staging --maximum-deltas 0 \
  --download-url-prefix https://updates.example.org/doolittle/staging/arm64/ \
  /path/to/staged-updates
```

Upload the immutable archives before publishing the signed feed. Check that
their URLs serve the exact generated bytes. Preserve earlier artifacts outside
the working directory used by `generate_appcast`. It may move older files.

Install the baseline on a clean Mac for the target architecture. Open
**Settings → Desktop → Check for updates**, confirm that the proposed version
is offered, and install it. Verify the relaunched version, existing profile,
and bundled CLI. While repeating the test, keep an unsaved file in the editor
and confirm the quit guard preserves it until the user consents. Test an
altered appcast and an altered archive against isolated staging fixtures.
Both must fail before an update is installed. Restore the original signed
staging files and confirm that checking and installing work again.
[Sparkle publishing guide](https://sparkle-project.org/documentation/publishing/)

If an update causes a regression, stop offering the bad version by restoring a
previous valid signed feed. Keep its prior notarized installer available for
manual recovery on compatible profiles. Devices that already installed the
bad version need a higher-version corrective release through the updater.
Check profile compatibility before recommending manual downgrades.
