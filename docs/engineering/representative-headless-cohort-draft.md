# Representative headless cohort — draft, not evaluation evidence

Status: planning only. No source manifest, frozen helper, prospective capture
receipt, or provider runs have been created for this cohort. This document is
not a completed predeclaration and does not supersede an existing cohort.

The question is whether a frozen candidate handles a small, representative
conversation/research/reliability set coherently without regressing objective
contracts. Coding evidence remains separate. Passing these proxies cannot
establish overall daily-use quality or installed-desktop behavior.

canonical report suite IDs: `headless-workflows-v7` emits suite
`headless-workflows`, version 7; `headless-sdk-web-research-v1` emits
`headless-sdk-web-research`, version 1. A future preflight must resolve and pin

All six tasks require human review. Per arm and repetition: six task runs,
13 objective checks and seven Doolittle CLI turns. If each task is selected in
its own headless harness launch, that is six harness launches, not seven.
For two repetitions per arm: 24 task runs, 52 checks, 28 Doolittle turns and
24 harness launches. Model/provider call counts are measured separately and
must not be inferred from these counts.

The configured Cloud `/research` task is excluded from this draft. The SDK
web task is not a substitute for that separately configured provider path.

## Prospective short blinded review boundary

The user selected short blinded reviews in chat. That permits prospective
synthetic response review, not recovery of previously discarded output or
retention of tool logs, commands, credentials or private task data.

Use the existing explicitly opt-in response callback only in a separately
validated capture path. Confirm its per-turn semantics, response byte caps and
complete/partial disposition before launch. Never scrape mixed CLI stdout for
responses: it contains unrelated diagnostics and may be truncated. Preserve
the two-turn response order for the session-memory task; do not present a lone
final line as evidence of the whole interaction.

The callback is an observation, not a cleanup or ownership attestation. Keep
its bounded response buffer volatile until the original report is written,
validated and bound after confirmed closure. If that acceptance boundary is
not reached, discard the buffer; do not recover retained task state or publish
an operational failure's response as a graded review sample. A capture-cap
failure must mark review coverage unavailable without throwing into grading.

Bind each review item to immutable report bytes and the exact task/turns. Retain
only the bounded synthetic final responses needed for review, with a closed
manifest and content digests; no free-text notes in the official review sidecar.
Reconcile captured bytes, counts and turn order with the report's
`responseSha256s` before accepting the capture. The official sidecar binds
report/task identity but does not validate this separate response manifest.
Keep the report itself content-free. Use directories owned by the current OS
account with mode `0700` and
exclusive no-follow files (`0600`), refuse substitution or unsafe ownership, and
do not use fallback locations. Capturing a response must not change its grade.

Randomize presentation labels independently of route and keep the hidden mapping
unread until ratings are submitted. Do not silently relabel an older review as a
new-candidate result. Report partial capture and missing human ratings honestly.
Any response that cannot safely fit the declared review boundary is unavailable
for that review rather than reconstructed or rewritten.

Ask the human for the six 1–5 rubric dimensions and closed critical-failure codes.
Use the official `createHumanReviewSidecar` validation with explicit human
attestation and one review per task in the bound report; never invent scores,
fill missing dimensions or substitute an automated preference. A critical
failure must retain the corresponding low rubric rating. Final-answer-only
ratings cannot attest unseen tool trajectories; identify that coverage limit.
The official schema has no N/A value and cannot authenticate reviewer identity.
If the human cannot rate a required dimension, keep the review incomplete;
never fill it automatically. Do not frame response-only scores as full
six-dimension trajectory quality, or efficiency scores as measured latency.

## Analysis and stopping rules

Report per-task objective numerators/denominators, execution completion and
human dimensions separately. Keep operational-failure events ineligible for
evaluation comparison. No report is not a failed objective grade; a safe,
failed-but-reported task remains a real graded observation.

Describe paired latency, ranges and available token signals only for eligible,
matched reports. Preserve unavailable cost and effective-route fields. Direct
harness phase clocks are partial coverage, not total harness overhead. With two
repetitions per arm and no controlled effective/worker routing, do not claim
causal speed, reliable token efficiency or population-level superiority.

Installed desktop provenance and controlled workflow runs are a separate gate.
Packaging, source tests and headless reports do not prove the installed app ran
this candidate or behaved correctly in its real client context.

See the [agent quality checklist](./agent-quality-eval-checklist.md) for the
existing measurement semantics and rubric. A subsequent completed predeclaration
must name its immutable evidence rather than marking this draft as executed.
